Answer first (pyramid)

Don't buy the AI chatbot yet. The delay isn't in answering students. It's in how tickets are routed, queued and escalated. Fixing intake routing and moving escalation to 50% of the SLA is estimated to lift compliance from 63% to about 79% (with a priority-first queue). This uses the existing team and tool. It should be piloted for 2 weeks before rolling out.

  • Priority is captured but ignored: High-priority tickets wait as long for a first response (19.3h median) as Low (16.3h), so only 21% meet 24h.
  • Misrouting compounds delay: 12% of tickets are reassigned. SLA falls 66% → 51% → 18% with each hop, and follow-ups rise 1.9 → 5.7.
  • Two departments hold the backlog: Fees & Finance 28% and Academics & Exams 45% (weekday office hours only), against IT 87%.
  • Escalation comes too late: a daily review escalates tickets open >48h (median 65h). That is after the deadline for every High ticket.

1One-page problem brief

Client: Student Services Helpdesk of a residential engineering college (about 1,800 students; 15 helpdesk staff across 5 departments plus triage). Sponsor: Dean of Student Affairs. Original request: "Buy an AI chatbot because tickets take forever." FDE reframing: find where the time actually goes first.

Current workflow (where the problem appears)

Student raises ticket→Triage: auto (portal) or manual queue (email/Other) ①→Department queue, priority unused ③→ First response→Misrouted? → back to triage ②→Work ⇄ waiting on student→Resolved→Reopen ⑤→Closed + CSAT Escalation: daily review of tickets >48h ④

Before the problem: intake and categorisation decide the first queue. After the problem: students chase with follow-ups, reopen tickets and give low CSAT.

Problem statement (SMART)

Only 63% of student helpdesk tickets resolved between 27 Jul and 20 Sep 2026 met their priority SLA (High 24h / Medium 72h / Low 120h), and only 21% of High-priority tickets did. Identify where in the ticket workflow delay accumulates and implement the highest-impact process fixes to raise SLA compliance to ≥75% (High-priority to ≥50%) within 8 weeks, using the existing helpdesk team and current ticketing tool (no new hires, no new software).

Facts (verified in data)

  • 1,230 unique tickets in 8 weeks; 3 intake channels
  • Draft SLA: High 24h / Medium 72h / Low 120h
  • Email tickets have no category; they go to manual triage
  • Escalation happens at a daily 10:00 review of tickets open >48h
  • Auto-reminder to the agent after 24h without a reply

Assumptions (need confirmation)

  • SLA clock pauses while "Waiting on Student"
  • SLA runs to the final resolution (after reopens)
  • Missing priority (email) = Medium, per policy default
  • "Exam Cell" = Academics & Exams; "Hostel" = Hostel & Maintenance
  • Cancelled and no-reply closures are excluded from the KPI

Unknowns (cannot get from data)

  • Why tickets are misrouted (no reason code)
  • Real agent effort (no time tracking)
  • Causal effect of escalation (only slow tickets get escalated)
  • Calendar vs business-hours SLA: not decided
  • Views of students who don't answer the CSAT survey
FDE judgement: a chatbot answers students faster, but the data shows first contact isn't the bottleneck. Queueing, routing and escalation are. Buying it now would be "building the request" instead of solving the problem.

Issue tree: "Why do tickets miss SLA?" (MECE by workflow stage)

These branches add up exactly: the model splits each ticket's total time into triage + first-response wait + re-routing + work + waiting-on-student + reopen cycle. They are mutually exclusive and collectively exhaustive, and verified in code (max gap 0.00h).

The API: "HTTP 200 on one page does not prove the job succeeded"

pipeline/retrieve.py
def _get(url: str, log) -> dict:
    """GET with retries: 5xx and 429 are retryable, 4xx is not."""
    for attempt in range(1, MAX_RETRIES + 1):
        try:
            with urllib.request.urlopen(url, timeout=10) as r:
                return json.loads(r.read())
        except urllib.error.HTTPError as e:
            if e.code == 429:
                wait = float(e.headers.get("Retry-After", 1))
            elif 500 <= e.code < 600:
                wait = 0.2 * 2 ** (attempt - 1)
            else:
                raise PipelineError(f"Non-retryable HTTP {e.code} for {url}")
            if attempt == MAX_RETRIES:
                log.error(f"API  HTTP {e.code} on attempt {attempt}/{MAX_RETRIES} -> giving up  ({url})")
                break
            log.warning(f"API  HTTP {e.code} on attempt {attempt}/{MAX_RETRIES} -> retry in {wait:.1f}s  ({url})")
            time.sleep(wait)

  • Missing priority (email tickets) = Medium, per draft SLA policy default.

Metrics are computed in SQL over the model (joins + aggregations)

pipeline/metrics.py
    "by_reassignment": """
        SELECT CASE WHEN reassign_count = 0 THEN '0 (routed right first time)'
                    WHEN reassign_count = 1 THEN '1 reassignment' ELSE '2+ reassignments' END AS segment,
               COUNT(*) AS tickets, ROUND(100.0 * AVG(sla_met), 1) AS sla_pct,
               ROUND(MEDIAN(net_resolution_hours), 1) AS median_net_h,
               ROUND(AVG(followup_count), 2) AS avg_followups,
               ROUND(100.0 * AVG(reopened), 1) AS reopen_pct
        FROM ticket_journey WHERE in_kpi_population = 1 GROUP BY 1 ORDER BY 1""",
pipeline/metrics.py
    "followups_vs_outcome": """
        SELECT CASE WHEN sla_met = 1 THEN 'met SLA' ELSE 'breached SLA' END AS segment, COUNT(*) AS tickets,
               ROUND(AVG(followup_count), 2) AS avg_followups,
               ROUND(AVG(c.rating), 2) AS avg_csat, COUNT(c.rating) AS csat_n
        FROM ticket_journey j LEFT JOIN fact_csat c ON c.ticket_id = j.ticket_id
        WHERE in_kpi_population = 1 GROUP BY 1""",

A MEDIAN aggregate is registered on the SQLite connection so medians are computed in SQL as well. Every segment table is saved to output/runs/<run_id>/segments/.

9Findings

So what? Breached tickets take 126h on average vs 42h for tickets that met SLA. The gap is mostly waiting for a first response (33h vs 12h), time inside slow teams (66h vs 20h) and re-routing (9h vs 2h). Waiting on the student is the same for both (about 3h), so students are not the cause.
HypothesisVerdictEvidence
H1 Misrouting drives breachesSUPPORTEDSLA 66% (0 hops) → 51% (1) → 18% (2+); breached tickets spend 9h re-routing vs 2h
H1b Manual triage alone drives breachesPARTLYManual queue waits 13.2h, but SLA is 61% vs 65% auto-routed; email 63% ≈ portal 62%. The wait is real but small next to department queues.
H2 Priority not used in queueingSUPPORTEDMedian first response High 19.3h ≈ Low 16.3h; SLA High 21% · Medium 64% · Low 86%
H3 Capacity / hours constrained teamsSUPPORTEDFees & Finance 28%, Academics 45% (Mon–Fri 9–17) vs IT 87%, Library 85%
H4 Escalation too lateSUPPORTEDMedian escalation at 65h (before breach) / 86h (after); 132 escalated after SLA passed, of which 1% met
H5 Weekend tickets are the main problemMINORWeekend 56% vs weekday 65%: a real gap, but only 206 tickets; a secondary driver

Association ≠ causation. Escalated tickets breach more (89% SLA when not escalated) partly because only slow tickets get escalated. Likewise, tickets with an auto-reminder (32% vs 75%) were already slow. The data shows escalation happens late. It cannot prove how much earlier escalation would help, which is why S3 below is a pilot, not a promise.

Recommendation (Situation → Complication → Resolution)

Situation: the helpdesk receives about 153 tickets a week across 5 teams with a draft 24/72/120h SLA. Complication: only 63% meet it (21% of High-priority), and the proposed fix, a chatbot, targets first contact, which is not where the time goes. Resolution: fix routing, queueing and escalation inside the current tool first. Revisit the chatbot for FAQ-style tickets once the process is sound.

Key success factors

  • Dean signs off one SLA definition before the pilot
  • Agents accept deadline-sorted queues (brief them on why)
  • Reason codes are actually filled in (make the field mandatory)

Risks

  • Finance and Academics capacity may still cap the gains; escalate a staffing discussion only with pilot evidence

10Dependable pipeline

What makes it repeatable

  • One command: python pipeline/run_pipeline.py; deterministic seed; a run_id per run
  • Immutable raw snapshot plus manifest (rows, sha256) per run
  • Rules as code, the same checks every run; results saved as JSON and Markdown
  • Structured log per run: time | level | stage | message
  • run_status.json with per-stage timing and exit code
  • Atomic publish: output/latest is replaced only after a full, gate-passing run (copy then rename)
  • 5 pytest tests: parsers, mappings, the SQL median, and the published model contract

Reliability evidence: does the pipeline get the right answer?

Because the data is synthetic, the generator's hidden ground truth lets me prove the pipeline is correct. That isn't possible with real data. tests/reconcile_with_truth.py compares:

MethodTickets usedSLA %Error vs truth (pp)
Ground truth (simulated)107763.50.0
Pipeline (cleaned + modelled)106963.1-0.4
Naive query on ticket table71464.61.1
The pipeline is within 0.4 pp of the truth and agrees on 99% of individual ticket verdicts (the differences are tickets whose missing priority was defaulted). A naive query on the ticket table looks plausible (64.6%), but it silently uses only 714 tickets. It drops DD/MM dates, status spellings and missing priorities, keeps duplicates, and times reopened tickets to their first fix. It is close only by accident: its errors partly cancel out, and its segment-level numbers would be wrong.

Two real bugs were caught this way while building. (1) A clock-skewed walk-in ticket that the first version of R07 missed: the rule was widened from "resolved before created" to "any event before created". (2) Reopened tickets that were still open were counted as resolved, now excluded by status. This is why the check exists.
