# 5-minute demo video: recording script

**What's on screen:** the 2-page submission PDF, the terminal, and the GitHub README. Every "Show" step below refers to one of these three.

**Goal of the video (from the brief):** what you found, what you built, what remains unknown.
**Length:** 5:00 (aim for 4:45). This is about 650 spoken words at a calm pace.

---

## Before you hit record (5 min setup)

1. Open a terminal in the repo and activate the environment:
   ```bash
   cd ~/FDE/campusdesk-fde-assignment
   source .venv/bin/activate
   clear
   ```
2. Increase the terminal font size (Cmd `+` three or four times) so the log is readable in the video.
3. Open these in separate windows, in this order:
   - the **2-page submission PDF** `report/CampusDesk_FDE_Submission_Lakshya_Mewara.pdf` (also in your Downloads folder)
   - the **GitHub repo** in your browser: https://github.com/LAKSHYAMEWARA0025/campusdesk-fde-assignment (README open)
   - the **terminal** from step 1
4. Keep this script on your **phone** (open it from GitHub: `docs/DEMO_SCRIPT.md`) so it doesn't appear in the recording.
5. Do one silent practice run of the pipeline so the first run in the video isn't slow:
   `python pipeline/run_pipeline.py --run-id live_practice`
6. Record with **QuickTime → File → New Screen Recording** (or Loom). Turn the microphone on, record the whole screen, and close notifications (Focus mode on).

> The `live_*` run folders are git-ignored, so running the demo doesn't dirty the repo.

## Script

### 0:00 – 0:35 · The ask, and the reframe
**Show:** PDF **page 1**, the top (title, name, roll number).

> "Hi, I'm Lakshya Mewara, roll number 24bcs10290. This is my FDE assignment, CampusDesk.
> The client is a college's Dean of Student Affairs. Their request was: students complain that helpdesk tickets take forever, so let's buy an AI chatbot.
> As an FDE, I didn't build the request. I first found out where the time actually goes. The data is synthetic but realistic, generated by a seeded script, so everything you'll see is reproducible."

### 0:35 – 1:25 · Stakeholders, workflow, problem statement
**Show:** PDF **page 1**. Scroll slowly past the Stakeholders table, the workflow strip and the SMART problem statement. Then optionally switch to the browser: README **§2** (the red-marked workflow flowchart).

> "On the brief you can see the stakeholders. The Dean owns the KPI, the Helpdesk Manager owns operations, and triage coordinators, department agents, students and the IT admin who owns the ticketing data are all involved.
> This is the current workflow. A student raises a ticket by portal, email or walk-in. It's either auto-routed or waits in a manual triage queue, lands in a department queue, gets worked, and is resolved and closed. The five red markers are where the data showed the problem: manual triage, misrouting, a queue that ignores priority, late escalation, and reopens.
> My SMART problem statement: only 63% of tickets meet their SLA, and only 21% of high-priority ones. The goal is to raise that to 75% in 8 weeks, with the same team and the same tool."

### 1:25 – 2:35 · Live pipeline run
**Show:** terminal. Type:
```bash
python pipeline/run_pipeline.py --run-id live_demo
```
While it runs:

> "This is the pipeline: retrieve, validate, model, metrics, publish.
> It pulls from four source types: a SQLite ticket database, a CSV audit-log export, a nested JSON survey export, and a paginated REST API.
> You can see the API failing with 500s and 429 rate limits. The pipeline retries with back-off, and it doesn't trust a single 200. It checks that all 4,550 records arrived before continuing.
> Everything raw is saved to a snapshot with checksums.
> Then there are fifteen business rules. Each one is a business assumption: one row is one ticket, nothing happens before a ticket is created, every ticket has a priority. Each gets PASS, WARN, FAIL or UNKNOWN. This run passes with caveats: things like DD/MM dates from the email importer, missing priorities and a walk-in desk with a wrong clock are fixed or disclosed, not silently cleaned. The SLA definition itself is UNKNOWN, because the Dean hasn't signed it off yet.
> Final KPI: 63.1% of 1,069 resolved tickets."

### 2:35 – 3:05 · It fails safely
**Show:** terminal. Type:
```bash
python pipeline/run_pipeline.py --run-id live_fail --simulate truncated_events
```
> "Now I simulate a broken export: half the audit log is missing. Rule R06 catches it, the gate fails, it exits with code 1, and nothing is published. The last good result in output/latest is left untouched. If the API is completely down, it fails at retrieval with exit code 2, also without publishing."

### 3:05 – 4:10 · What I found
**Show:** PDF **page 2**: the 4 number tiles at the top, then the SLA chart (by department / priority / reassignments) and the 4 bullets under it. Optional: the README *Findings & recommendation* section has the "where the time goes" chart for the 126h vs 42h point.

> "Here's what the data shows. Breached tickets take 126 hours on average against 42 for on-time ones. The difference is waiting for a first response, time inside slow teams, and re-routing, not students being slow to reply.
> Four findings. One: priority is captured but ignored. High-priority tickets wait as long as low ones, so only 21% meet 24 hours. Two: misrouting compounds. Routed right first time, 66% meet SLA. After two or more reassignments, only 18%. Three: Fees and Finance at 28% and Academics at 45% hold the backlog, against IT at 87%. Four: escalation happens at a daily review of tickets open more than 48 hours, at a median of 65 hours, which is already past the deadline for every high-priority ticket. 132 tickets were escalated only after they'd breached.
> I'm careful about causation: escalated tickets look worse partly because only slow tickets get escalated."

### 4:10 – 4:40 · Recommendation
**Show:** PDF **page 2**, the **Recommendation** paragraph. Optional: the README *Findings & recommendation* section for the what-if table (S1 / S2 / S3 → about 79%).

> "So my recommendation is: don't buy the chatbot yet. Fix intake routing, escalate at 50% of each ticket's SLA instead of after 48 hours, and sort queues by deadline. Re-scoring the measured journeys estimates about 79%, above the 75% target. The escalation effect is an assumption, so the plan starts with a two-week pilot and leading indicators: reassignment rate, triage wait, and on-time escalations."

### 4:40 – 5:00 · Reliability and unknowns
**Show:** PDF **page 2**, the **Reliability** line and **4 · What remains unknown**. Finish on the **GitHub repo** page: scroll the README briefly and point at the green **pipeline** badge (CI passing).

> "Because the data is synthetic, I could prove the pipeline is right. It lands within 0.4 points of the hidden ground truth, while a naive query silently drops 42% of tickets.
> What remains unknown: why tickets are misrouted, since there's no reason code; real agent effort; the causal effect of escalation; and the SLA definition sign-off. Each has an owner and a next step in the report. Thank you."
