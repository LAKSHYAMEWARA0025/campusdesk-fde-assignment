# CampusDesk — From Ambiguous Problem to Dependable Data Workflow

**FDE Assignment · Lakshya Mewara · Roll No. 24bcs10290 · Batch 2024-28**

> *"Students keep complaining that helpdesk tickets take forever. Before we buy an AI chatbot for the helpdesk, find out what is actually happening."* (Dean of Student Affairs)

This repo investigates a college **Student Services Helpdesk** the way an FDE would. It covers stakeholder discovery, the workflow map, a SMART problem statement, the KPI and scope, the source map, and retrieval from **4 source types** (SQL, CSV, JSON, paginated REST API). It then profiles and validates the data, models the workflow, and computes metrics in a **repeatable pipeline with logging, a validation gate and safe failure handling**.

**Data:** fully **synthetic but realistic**, generated by `generator/generate_data.py` (seed 42). The generator simulates the real workflow (triage queue, working hours, misrouting, waiting-on-student pauses, reopens, escalations, CSAT). It then injects real-world data problems: duplicates, mixed date formats, category and status variants, missing priority, orphan events, clock skew, a stale denormalised column and a messy survey export.

## Headline result
| | |
|---|---|
| **Project KPI: SLA compliance** | **60.5%** of 1,083 resolved tickets (target: **75% within 8 weeks**) |
| Worst segments | High priority **21%** · Fees & Finance **34%** · Academics & Exams **44%** |
| Biggest drivers | Misrouting (0 → 1 → 2+ reassignments: 63% → 45% → 31%); manual triage wait of 12.9h; priority not used for queueing; escalation fires at a median of 64h |
| Recommendation | **Don't buy the AI chatbot yet.** Fix intake routing and move escalation to 50% of the SLA (estimated about 79%). Pilot these first. |
| Reliability | The pipeline recovers the simulated true KPI within **0.1 pp**. A naive query is off by 1.8 pp and silently drops 38% of tickets. |

## Repo layout
```

                                csat_survey_export.json, sla_policy.json, portal_api_data.json
api/mock_portal_api.py          mock Portal REST API (paginated, flaky: 500 / 429)
pipeline/
  run_pipeline.py               orchestrator: retrieve -> validate -> model -> metrics -> publish
  retrieve.py                   SQL + CSV + JSON + API retrieval, retries, completeness proof, raw snapshot
  validate.py                   profiling, 15 business rules -> PASS/WARN/FAIL/UNKNOWN gate, safe fixes
  model.py                      workflow model (dims, facts, ticket_journey) -> warehouse.db
  metrics.py                    KPI + supporting metrics + segments in SQL
  charts.py                     report charts
analysis/what_if.py             sizing of recommended fixes (estimates, assumptions stated)
tests/test_pipeline.py          unit + contract tests (pytest)
tests/reconcile_with_truth.py   pipeline vs hidden ground truth vs naive query
notebooks/CampusDesk_FDE_Walkthrough.ipynb   executed walkthrough of every stage
output/latest/                  last PUBLISHED run (only replaced when the gate passes)
output/runs/<run_id>/           every run, including failed ones
logs/                           one log file per run
```

## Run it
```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python generator/generate_data.py                                   # optional: regenerate source systems (deterministic)
python pipeline/run_pipeline.py --run-id demo_run                   # normal run -> exit 0, published
python pipeline/run_pipeline.py --run-id demo_fail_api_outage --simulate api_outage           # exit 2, nothing published
python pipeline/run_pipeline.py --run-id demo_fail_truncated_events --simulate truncated_events # exit 1, gate FAIL
python tests/reconcile_with_truth.py && python analysis/what_if.py
python -m pytest -q tests
```
The pipeline starts the mock API itself if it isn't running. Exit codes: `0` published · `1` stopped by validation gate · `2` stage failure.

## Failure handling (summary)
| Failure | Detection | Behaviour |
|---|---|---|
| API 500 / 429 / connection error | HTTP status | exponential back-off (honours `Retry-After`), up to 6 attempts per page |
| API silently incomplete | fetched count and unique ids vs `total_records` | stage fails, run aborted |
| Partial / truncated export | R06: tickets with a lifecycle below 98% | gate FAIL, nothing published |
| Business-rule breach above threshold | any rule = FAIL | gate FAIL, nothing published |
| Known, disclosed issues | WARN / UNKNOWN | published as **PROVISIONAL** with the caveats listed in `metrics.json` |

In every failure case `output/latest` keeps the last good run. It is only replaced after a complete, gate-passing run, via a copy and rename.
